## 0. Instructions to Claude Code

You are building a small, offline desktop app that **teaches game development** through:
- **Papers**: lecture-style reading documents (Markdown).
- **Questions**: Khan Academy-style practice (one question per screen, Check button, progressive hints, explanation after answering, mastery levels).

The app does **not** write lessons itself. Lessons are generated by Claude in a separate chat (claude.ai), copied as text, and imported into the app. The app is a **player + progress tracker**. That split keeps the app small, free (no API key), and updatable without rebuilding: new content and new prompt rules are just files.

- Build in the milestone order in Section 15. Commit to git after each milestone with a clear message.
- Only stop to ask Elliott something if it blocks you (e.g. a toolchain install that needs his permission). Otherwise make the reasonable choice and note it in `DECISIONS.md`.

## 1. Who it's for and design principles

**User:** Elliott, a self-taught game-dev learner. He is autistic and has ADHD. The app's design must make starting cheap and remove ambiguity.

**Principles (these override taste):**
1. **One primary action per screen.** Home screen = one big "Next" button.
2. **Zero ambiguity.** Every lesson shows "Done means: …" (the exact finish condition). Every button label says exactly what it does ("Check answer", not "Submit").
3. **No shame mechanics.** No streaks, no hearts/lives, no red "WRONG". A wrong answer shows **"Not yet"** in yellow, plus a hint option.
4. **Predictable layout.** Same structure every time. No surprise popups, no auto-playing anything.
5. **Low friction to resume.** App reopens exactly where he left off.
6. **Keyboard-first.** Everything doable without the mouse.
7. **Reduced motion respected.** Animations ≤150 ms; off entirely if the OS prefers reduced motion or the setting is off.

## 2. Non-goals (do not build in v1)

- Accounts, cloud sync, telemetry, analytics, network calls of any kind.
- Calling an AI API from the app. (Possible v2, behind a setting. Not now.)
- A front-end framework (React/Vue/Svelte). Vanilla TypeScript only.
- A database. Plain files only.
- Gamification (XP, badges, leaderboards, streaks).
- A lesson editor. Lessons are edited as text files or regenerated.

## 5. Lesson file format (the contract)

This format is the most important part of the project. The app parser, the validator, the generator prompt and the sample lessons must all match it exactly.

### 5.1 Structure

A lesson is one UTF-8 text file named `<id>.lesson.md`:

1. **YAML frontmatter** between `---` lines.
2. **Paper body** in Markdown.
3. **Question blocks** anywhere in the body, fenced with **tildes**:
   ```
   ~~~question
   <YAML>
   ~~~
   ```
   Tildes are used so that GDScript code fenced with backticks can appear inside question prompts without breaking the fence.

Questions placed **inside** the paper render inline as "Check yourself" cards. Questions after the heading `## Practice` form the practice set. **All** questions, inline or not, are included in Practice mode, in file order.

**Parsing approach:** don't depend on markdown-it for question blocks. First split the file line by line: a line exactly `~~~question` opens a block, the next line exactly `~~~` closes it. Record line numbers for error messages. Replace each block in the paper with a placeholder `<!--Q:<id>-->` before rendering the Markdown.

**Import tolerance:** if the pasted text contains an outer fence (a line of 4 or more backticks, optionally followed by the word `lesson`, and a later closing line of the same number of backticks), keep only what is between those two lines. Everything outside the outer fence is chat text and is discarded.

### 5.2 Frontmatter fields

| Field | Required | Type | Rules |
|---|---|---|---|
| `id` | yes | string | `^[a-z0-9][a-z0-9.-]*$`, unique. Becomes the file name. |
| `title` | yes | string | |
| `track` | yes | enum | `C` `X` `P` `D` `A` `S` `N` (Section 12) |
| `unit` | yes | string | Unit id from `curriculum.json`, e.g. `C.loops`. Unknown unit = **warning**, not error. |
| `tier` | yes | int 0–4 | |
| `energy` | yes | int 1–3 | 1 = 5–10 min, 2 = ~25 min, 3 = 45–90 min |
| `minutes` | yes | int | Estimated total time. |
| `paper_type` | yes | enum | `concept` `worked-example` `case-study` `brief` `reference` |
| `done_means` | yes | string | Exact finish condition, shown in the lesson header. |
| `summary` | yes | string | One sentence, shown in Library. |
| `prerequisites` | no | list of lesson ids or unit ids | Missing ones show as a note, never a block. |
| `tags` | no | list of strings | Used for weak-spot tracking. |
| `glossary` | no | list of `{term, definition}` | Every new term the lesson introduces. |
| `seed` | no | `{theme, verb, constraint}` | From the learning engine's random tables. |
| `version` | yes | int | Format version. Currently `1`. |

### 5.3 Question fields (all types)

| Field | Required | Notes |
|---|---|---|
| `id` | yes | Unique within the lesson, e.g. `q1`. Global key = `<lessonId>#<id>`. |
| `type` | yes | See 5.4. |
| `prompt` | yes | Markdown (use `\|` YAML block scalar for multi-line). |
| `hints` | no | List, revealed one at a time. Max 3. The first hint is a nudge; the last one almost gives the answer. |
| `explanation` | yes | Markdown. Shown after answering (right or wrong). Explains *why*. |
| `tags` | no | Extra skill tags. |

### 5.4 Question types

| `type` | Extra fields | Correct when |
|---|---|---|
| `mcq` | `choices` (list, 2–6), `answer` (letter, e.g. `B`), optional `feedback` (map letter → text shown if that wrong choice is picked) | Selected letter = `answer`. Letters A, B, C… follow list order. **Display order is shuffled, but labels stay attached to their choice.** |
| `multi` | `choices`, `answer` (list of letters) | Selected set = answer set exactly. |
| `numeric` | `answer` (number), `tolerance` (number, default 0), optional `unit` (string shown after input) | abs(input − answer) ≤ tolerance. Accept `,` or `.` as decimal separator. |
| `text` | `accept` (list of strings), `case_sensitive` (default false) | Trimmed input, with internal whitespace collapsed, matches any `accept` entry. |
| `fill` | prompt contains `___` (three underscores) per blank; `blanks` = list of lists of accepted strings, one list per blank in order | Every blank matches (same rules as `text`). |
| `order` | `items` (list in **correct** order, 3–7) | Displayed shuffled; correct when he reorders them exactly. Reordering via drag **and** keyboard (select + ↑/↓). |
| `match` | `pairs` (list of `[left, right]`, 3–6) | Every left matched to its right. Right column shuffled. |
| `reflect` | `model_answer` (Markdown), optional `rubric` (list of strings) | Not auto-graded. He writes an answer, presses "Show model answer", then rates himself: **Got it / Partly / Not yet**. Used heavily for design and planning skills. |
| `task` | `instructions` (Markdown), `done_means` (string) | An action outside the app (e.g. "make this in Godot"). Checkbox "I did this". Not scored, not reviewed. |

````

title: Core Loops
track: C
unit: C.loops
tier: 1
energy: 2
minutes: 25
paper_type: concept
done_means: "You can write the core loop of any game as 3–5 arrows and say why it repeats."
summary: "What a core loop is, how to find one, and how to design one."
tags: [core-loop]
glossary:
  - term: core loop
    definition: "The cycle of actions a player repeats for most of the game."
version: 1
---

# Core Loops

A **core loop** is the cycle of actions a player repeats ...

~~~question
id: q1
type: mcq
prompt: "Which of these is a core loop?"
choices:
  - "Title screen → options → quit"
  - "Explore → fight → collect loot → upgrade → explore"
  - "Tutorial → credits"
answer: B
feedback:
  A: "These are menu screens. They don't repeat during play."
explanation: "B repeats for the whole game, and each step leads into the next."
~~~

## Practice

~~~question
id: q2
type: order
prompt: "Put Tetris's core loop in order."
items:
  - "A piece appears"
  - "Move and rotate it"
  - "Drop it"
  - "Full lines clear"
explanation: "Clearing lines makes space, which lets the next piece appear safely."
~~~

~~~question
id: q3
type: reflect
prompt: "Write the core loop of a game you played this month, as arrows."
model_answer: |
  Example (Stardew Valley): plant → water → harvest → sell → buy seeds → plant.
rubric:
  - "3–5 steps"
  - "The last step leads back into the first"
explanation: "If your loop doesn't close back on itself, it's a sequence, not a loop."
~~~
````

### 5.6 Validation

`validate.ts` returns `{errors, warnings}`. Each entry has: line number, field, plain-English message, and a suggested fix. Examples:
- `line 14, q2.answer: "E" is not one of the choices A–C.`
- `line 3, track: "Design" must be one of C, X, P, D, A, S, N.`

**Errors block import. Warnings don't.** The Import screen has a button **"Copy error report"** that copies all errors as plain text, with a header line: `Fix these errors in the lesson file and output the full corrected lesson:`. That lets Elliott paste the report straight back to Claude.

## 7. Learning systems (exact rules)

### 7.1 Scoring a question attempt
- Correct on the first try, no hints: **1**
- Correct after hints or a second try: **0.5** (`correct-hinted`)
- Wrong after 2 tries, or "Show answer": **0** (`wrong`)
- Reflect: Got it **1**, Partly **0.5**, Not yet **0**
- Task: not scored.

Each question allows **2 tries**. After the first wrong try: show "Not yet" + per-choice feedback if present, and offer "Hint". After the second wrong try: show the correct answer + explanation.

### 7.2 Review scheduling (Leitner system)
The **Leitner system** sorts questions into numbered boxes. A correct answer moves a question up a box, so it comes back less often. A wrong answer moves it back to box 1.
- Box intervals in days: box1 = 1, box2 = 2, box3 = 4, box4 = 8, box5 = 16.
- After first practice: score 1 → box 2, otherwise box 1.
- In review: score 1 → box + 1 (max 5). Score 0.5 → stay in the same box. Score 0 → box 1.
- `due = today + interval(box)`.
- Review session = up to **15** due questions, oldest due date first. `task` questions are never reviewed.
- Home shows "Review (N due)" only when N > 0.

### 7.3 Unit mastery (Khan-style levels)
Per unit, computed from question history (never stored, always recomputed):

| Level | Rule |
|---|---|
| Not started | No practiced lessons in the unit. |
| Familiar | ≥1 lesson in the unit practiced with score ≥ 0.7. |
| Proficient | ≥5 review answers in the unit that happened ≥2 days after `firstSeen`, averaging ≥ 0.8. |
| Mastered | ≥8 review answers that happened ≥7 days after `firstSeen`, averaging ≥ 0.9. |

Levels only go up. Show the rule text on hover in the Map, so the rules are never hidden.

### 7.4 Energy
"Next" asks for energy (three buttons: 1, 2, 3, with keys `1` `2` `3`). The answer is used to choose a lesson from the library, and to fill the prompt context (Section 8).

**Picking the next lesson from the library**, in order:
1. A lesson in progress → resume it.
2. Unpracticed lessons with `energy` ≤ chosen energy, in this order: lessons whose prerequisites are met, then lower tier, then oldest imported.
3. If there are none: show **"No lesson ready. Ask Claude for one →"**, which goes to the Ask screen with the energy pre-filled.

## 8. The prompt loop (how lessons get made)

This loop is the "updatable" part: Elliott asks for anything; Claude turns it into a lesson in the exact format.

**Ask screen:**
1. A text box: "What do you want to learn? (leave empty for 'next in curriculum')".
2. The energy picker.
3. Button **"Copy prompt for Claude"**, which copies:
   - the full contents of `<AppData>/generator-prompt.md`, then
   - the **learner context** block (built by `context.ts`), then
   - his request.
4. A line of instructions under the button: "Paste into Claude. Copy the lesson it gives you. Then go to Import."

**Learner context block format** (plain text, compact):
```
=== LEARNER CONTEXT ===
date: 2026-11-02
energy: 2
request: "teach me signals in Godot"   (or: next)
lessons_practiced: 7
unit_mastery: C.verbs=Familiar, C.loops=Familiar, X.actions=Proficient, P.tour=Familiar
recent (last 5): c-core-loops-01 0.83 | x-timebox-01 1.0 | ...
weak_tags (avg < 0.6, min 3 answers): vectors, delta-time
known_terms: core loop, MDA, time-box, node, scene, ...
existing_ids: c-core-loops-01, x-timebox-01, ...
used_seeds (last 10): lighthouse/push, bakery/stack, ...
curriculum_units: <compact list of unit ids + titles from curriculum.json>
=== END CONTEXT ===
```

**Import screen:** a big paste box, a button **"Import lesson"** (also `Ctrl+Enter`), and the validation report. On success: save the file, show "Imported: <title>" with button **"Open lesson"**. Also allow importing `.lesson.md` files by drag-and-drop or a file picker. If an id already exists: ask "Replace existing lesson?" (Replace / Keep both: append `-2`).

## 10. Paper types (what each looks like)

| `paper_type` | Purpose | Structure |
|---|---|---|
| `concept` | Teach an idea | Hook (a real game example) → definition → 2–3 examples → common mistakes → summary |
| `worked-example` | Show a process step by step | Goal → steps with code/diagrams → "why each step" → variation for him to try |
| `case-study` | Dissect a real game | Context → the system → how it works → why it works → what to steal |
| `brief` | A design or production assignment | Situation → constraints (seed) → deliverable → "done means" → reflection |
| `reference` | A cheat sheet to come back to | Short sections, tables, no long prose |

Diagrams: allow ```` ```svg ```` blocks containing inline SVG. Sanitise them with DOMPurify's SVG profile and render them as figures.

## 11. Generator prompt

Create `content/generator-prompt.md` with **exactly** the text between the two marker lines below (not including the markers).

<<<BEGIN FILE: content/generator-prompt.md>>>
# Lesson generator — instructions for Claude

You are generating ONE lesson file for Elliott's game-dev learning app "Nordlys". The app parses your output automatically, so the format must be exact.

## About the learner
- Self-taught game-dev learner. Goal: be a versatile solo developer (design, planning, code, art, sound, writing).
- Autistic and has ADHD. So: literal language, no ambiguity, short sections, concrete examples, an exact finish condition.
- Engine: Godot 4 with GDScript.

## Output rules
1. Output exactly one lesson, wrapped in an outer fence of FOUR backticks with the info string `lesson`. Write nothing after the closing fence.
2. Follow the FORMAT SPEC below exactly. Use YAML block scalars (`|`) for multi-line text.
3. Question blocks use TILDE fences (`~~~question` … `~~~`). Code inside questions uses backtick fences.
4. Pick an `id` that is not in `existing_ids`. Pattern: `<track letter lowercase>-<topic>-<nn>`, e.g. `p-signals-01`.

## Choosing the lesson
- If `request` is specific: teach exactly that, at a tier that fits `unit_mastery`.
- If `request` is `next`:
  - Target track shares: C 30%, X 25%, P 20%, D 10%, A 5%, S 5%, N 5%.
  - Pick the track furthest below its share in `recent`. Never the same track 3 times in a row.
  - Within the track, pick the lowest unit not yet Familiar whose prerequisites are Familiar.
  - Prefer topics in `weak_tags` when possible.
- Every 5th lesson (when `lessons_practiced + 1` is a multiple of 5): an integration lesson combining two tracks, one of them C or X.

## Sizing by energy
| energy | minutes | paper length | questions |
|---|---|---|---|
| 1 | 5–10 | 250–450 words | 3–4 |
| 2 | 20–30 | 700–1200 words | 6–8 |
| 3 | 45–90 | 1500–2500 words | 9–12, including one `task` |

## Question mix rules
- Use at least 3 different question types per lesson (2 for energy 1).
- C (design) and X (production) lessons: at least one `reflect` question. Design skill is judgement, so not everything can be auto-graded.
- P (programming) lessons: at least one "what does this code do / print" question, and one `fill` or `order` using real GDScript.
- Put 1–2 questions inline in the paper as checks. Put the rest under `## Practice`.
- Wrong choices must be plausible, based on real misconceptions. Add `feedback` for wrong choices when the misconception is worth explaining.
- Hints progress: hint 1 = a nudge, hint 2 = narrows it down, hint 3 = nearly the answer.
- Every question has an `explanation` that says WHY, not just what.

## Writing rules
- Literal and concrete. Banned words: "simply", "just", "obviously", "easy", "explore", "play around", "get familiar with", "etc.".
- Every term not in `known_terms`: bold it the first time it appears, define it in one plain sentence right there, and add it to `glossary`.
- Use examples from real games (name the game and the exact moment or system).
- Short paragraphs (max 4 sentences). Use tables and numbered steps where they help.
- `done_means` must be checkable: the exact thing he can do or produce when finished.
- Use Godot 4 syntax ONLY. Never Godot 3. Examples: `CharacterBody2D`, built-in `velocity` + `move_and_slide()` with no arguments, `@export`, `@onready`, `signal_name.connect(callable)`, `signal_name.emit()`, `get_tree().change_scene_to_file()`, `FileAccess`, `create_tween()`.
- Maths: use `$...$` / `$$...$$` (KaTeX). Always explain a formula in words and with a game example. Assume no prior school maths beyond arithmetic.
- Diagrams: you may use a ```svg block with simple inline SVG (max ~40 elements).

## FORMAT SPEC (version 1)

Frontmatter fields: id, title, track (C|X|P|D|A|S|N), unit (from curriculum_units), tier (0–4), energy (1–3), minutes, paper_type (concept|worked-example|case-study|brief|reference), done_means, summary, prerequisites (optional list), tags (optional list), glossary (optional list of {term, definition}), seed (optional {theme, verb, constraint}), version: 1.

Question types and their fields (all types need: id, type, prompt, explanation; optional: hints (max 3), tags):
- mcq: choices (2–6), answer (one letter, A = first choice), feedback (optional map letter → text)
- multi: choices, answer (list of letters)
- numeric: answer (number), tolerance (number), unit (optional)
- text: accept (list of accepted strings), case_sensitive (default false)
- fill: prompt with ___ per blank; blanks (list of lists of accepted strings)
- order: items (in CORRECT order, 3–7)
- match: pairs (list of [left, right], 3–6)
- reflect: model_answer, rubric (optional list)
- task: instructions, done_means

## 16. Edge cases to handle

- Pasted text with Windows line endings (`\r\n`) or a byte-order mark.
- Claude output that includes chat text before or after the outer fence.
- A lesson re-imported with the same id after Elliott already has progress on it: keep the progress for question ids that still exist; drop the rest.
- Corrupt `progress.json`: load the newest valid backup and show a one-line notice.
- Very long lessons: lazy-render code highlighting.
